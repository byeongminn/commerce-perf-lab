# commerce-perf-lab

쇼핑몰 상품 탐색 앱에서 프론트엔드 실무 기술을 연습하고, 개선 전후를 측정해 남기는 실험 레포입니다.

| 연습할 것       | 기능                             |
| --------------- | -------------------------------- |
| 가상 스크롤     | 상품 수천~만 개 목록             |
| 낙관적 업데이트 | 찜(하트) 토글, 장바구니 담기     |
| 폼 리렌더       | 필터 패널 + 주문서 폼            |
| 이미지 LCP      | 상품 상세 대표 이미지, 메인 배너 |

## 기술 스택

Next.js (App Router) · TypeScript · pnpm · TanStack Query v5 · React Hook Form · Vitest · @faker-js/faker

## 실행

```bash
pnpm install
pnpm dev        # http://localhost:3000
```

| 스크립트         | 설명                                               |
| ---------------- | -------------------------------------------------- |
| `pnpm lint`      | ESLint                                             |
| `pnpm typecheck` | 라우트 타입 생성(`next typegen`) 후 `tsc --noEmit` |
| `pnpm test`      | Vitest                                             |
| `pnpm format`    | Prettier                                           |

## 더미 데이터와 API

별도 백엔드 없이 Faker와 Route Handler로 데이터를 만듭니다 (`src/server/data.ts`).

- 고정 시드(`faker.seed(42)`)를 써서 매번 같은 데이터가 나옵니다. 전후 측정을 같은 조건에서 비교하기 위해서입니다.
- 상품 개수는 기본 10,000개이고 `PRODUCT_COUNT` 환경 변수로 바꿀 수 있습니다.
- 찜 · 장바구니 상태는 서버 메모리에 저장하므로 dev 서버를 재시작하면 초기화됩니다.

| 메서드        | 경로                 | 설명                                                                                                                            |
| ------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| GET           | `/api/products`      | 목록. `category` `color` `size` `minPrice` `maxPrice` `sort`(`latest` · `price_asc` · `price_desc` · `rating`) `cursor` `limit` |
| GET           | `/api/products/[id]` | 상세                                                                                                                            |
| POST · DELETE | `/api/wishlist/[id]` | 찜하기 · 찜 해제                                                                                                                |
| GET · POST    | `/api/cart`          | 장바구니 조회 · 담기 (`{ productId, quantity }`)                                                                                |

### 지연 · 실패 흉내

낙관적 업데이트의 롤백을 재현하려고 모든 API에 지연과 실패를 줄 수 있습니다.

- 화면 왼쪽 아래 패널에서 지연(ms)과 실패율을 고르면 모든 요청에 헤더로 붙습니다.
- 직접 호출할 때는 헤더 `x-mock-delay` · `x-mock-fail` 또는 쿼리 `?delay=1000&fail=0.5`를 씁니다. `fail`은 실패 확률(0~1)이고 1이면 항상 실패합니다.

## 실험

각 실험은 개선 전 구현을 지우지 않고 남겨서 `?variant=` 쿼리 파라미터로 전환해 비교합니다.
실험별 섹션(문제 → 접근 → 트레이드오프 → 측정 결과)은 해당 단계를 진행하면서 추가합니다.

### 실험 2. 낙관적 업데이트 (찜 · 장바구니)

`/products?variant=server` (개선 전) · `/products?variant=optimistic` (개선 후)

#### 문제

서버 응답을 받은 뒤에 화면을 바꾸면, 네트워크가 느릴 때 하트를 눌러도 한참 반응이 없다.
그렇다고 단순하게 낙관적 업데이트를 하면 다음 문제가 생긴다.

- 실패 시 캐시 전체를 스냅샷으로 되돌리면, 그사이 성공한 다른 상품의 찜까지 함께 되돌아간다
- 낙관적으로 +1 한 뒤 성공 응답에서 또 +1 하면 찜 개수가 두 번 늘어난다

#### 접근

- 개선 전: 성공 응답 후 `setQueriesData`로 해당 상품만 갱신 (목록 invalidate 없음)
- 개선 후: `onMutate`에서 `cancelQueries` 후 즉시 캐시 변경
  - 스냅샷은 캐시 전체가 아니라 **그 상품 하나의 이전 상태**만 저장하고, 실패하면 그 상품만 복원
  - 성공 응답과 롤백 때는 값을 더하거나 빼지 않고 **덮어쓴다** → 개수가 두 번 바뀌지 않음
  - 장바구니는 실패한 요청의 수량만 빼고, 합계는 항목에서 매번 다시 계산
- 캐시를 바꾸는 로직은 순수 함수(updater)로 분리하고, 연속 클릭 · 부분 실패 시나리오를 renderHook 테스트로 검증

#### 트레이드오프

- 같은 상품의 찜 요청은 진행 중이면 버튼을 비활성화했다. 찜은 토글이라 같은 상품에 요청이 겹치면 어느 응답이 최종인지 보장하기 어렵기 때문. 다른 상품은 연속으로 누를 수 있다
- 실패하면 사용자는 "켜졌다가 꺼지는" 화면을 보게 된다. 지금은 따로 알림을 띄우지 않는다
- 코드가 서버 응답 후 반영 방식보다 복잡하다 (스냅샷 · 롤백 · 요청 취소)

#### 측정 결과

찜 버튼을 클릭한 시점부터 하트가 바뀐 뒤 다음 프레임이 그려질 때까지 (`performance.now()`, 조건별 5회).
개발 모드 서버, Chrome, 스크립트 클릭(`button.click()`)이라 실제 마우스 입력 처리 시간은 빠져 있다.

| 패널 지연 | 개선 전 (server)        | 개선 후 (optimistic) |
| --------- | ----------------------- | -------------------- |
| 0ms       | 평균 37ms (25~60)       | 평균 13ms (12~16)    |
| 300ms     | 평균 337ms (334~341)    | 평균 18ms (15~20)    |
| 1000ms    | 평균 1037ms (1029~1042) | 평균 18ms (17~21)    |

실패율 50% · 지연 1000ms에서 6개 상품을 연속 클릭: 6개 모두 즉시 바뀌었고, 실패한 3개만 원래대로 돌아갔으며 성공한 3개는 유지됐다. 6개 모두 최종 화면이 서버 상태와 같았고 찜 개수가 두 번 바뀐 경우는 없었다.
